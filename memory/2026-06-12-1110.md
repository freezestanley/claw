## 一、需要先澄清的关键问题

### 1. SSO 类型
- **哪种 SSO 协议？** 这是最大分叉点：
  - **OAuth2 / OIDC**（最常见，如 Google / 企业 IdP / Auth0 / Keycloak）
  - **CAS**（高校/传统企业常见）
  - **SAML**（企业老系统，浏览器侧基本不直接做，需后端）
  - **自建 token 登录**（公司内部 `/login` 换 JWT）
- **是哪家 IdP？** 自建的，还是飞书/企业微信/Google/Okta 这类？

### 2. SPA 还是带后端
WebGen 默认产出**纯前端单页面**。但 SSO 的安全实现强依赖一个东西：**回调与 token 交换该放哪？**
- **方案 A（纯前端 SPA + PKCE）**：OIDC Authorization Code + PKCE，token 存浏览器。无需自己写后端，但 token 暴露在前端。
- **方案 B（有 BFF/代理后端）**：登录回调和 token 交换在服务端，前端只拿 httpOnly cookie。更安全，但需要一个后端（哪怕是轻量 Node/Workers 代理）。

→ **你这边接口请求本来就要走代理**，所以我倾向 **方案 B**，正好和 WebGen 的本地 `/api` 代理策略一致。

- 鉴权方式：`Authorization: Bearer <token>` 还是 cookie？

## 二、推荐方案（基于 WebGen 现有约束）

我先给一个**默认推荐架构**，你确认后再落地：

```
浏览器 (SPA, 单页面)
   │  Axios (统一封装)
   │  ├─ 请求拦截器: 注入 token / 处理鉴权
   │  └─ 响应拦截器: 401 → 触发 SSO 登录 / 刷新 token
   ▼
本地 /api 代理 (Vite dev proxy / 生产 BFF)
   │  ├─ /api/*       → 转发到远端业务 API
   │  └─ /auth/*      → SSO 登录、回调、token 交换 (服务端持有 client_secret)
   ▼
远端业务 API  +  SSO IdP (OIDC/OAuth2/CAS)
```

### 核心设计点

**1. Ajax 层（Axios 统一封装）**
- 单例 `request.js`：统一 baseURL、超时、拦截器
- 请求拦截器自动注入鉴权
- 响应拦截器统一处理 `401 → 跳登录`、`403`、错误提示
- 开发期走 Vite `/api` 代理，避免 CORS

**2. SSO 登录流（推荐 OIDC + PKCE 或 BFF）**
- 未登录访问 → 重定向到 IdP 授权页
- IdP 回调 → 拿 code → 换 token（前端 PKCE 或后端 BFF）
- 登录态维护：内存 + 刷新机制
- 登出：清 token + 通知 IdP

**3. 路由守卫**
- 单页面内做轻量「登录态门禁」：未登录显示登录引导，已登录显示业务内容

## 一、对齐后的关键约束

| 维度 | 你的情况 | 对方案的影响 |
|------|---------|------------|
| SSO | 自建 | 登录/回调/校验都是你自己的端点，不依赖标准 OIDC SDK |
| 鉴权 | cookie + 请求头 | cookie 走浏览器自动携带，header 需手动注入；要处理跨域 cookie |
| 远端服务 | **一个项目对多个** | 必须支持**多 upstream 代理**，不能单一 baseURL |

→ 第三点是这次方案的核心：**多服务代理 + 多 client 实例**。

## 二、整体架构

```
浏览器 (SPA 单页面)
  │
  ├─ http/ 多实例 Axios
  │    ├─ apiUserClient   → /api/user/*
  │    ├─ apiOrderClient  → /api/order/*
  │    └─ apiXxxClient    → /api/xxx/*
  │    每个 client 共用同一套拦截器:
  │      请求: withCredentials=true(带cookie) + 注入 header token
  │      响应: 401 → 跳自建 SSO 登录
  │
  ▼ 本地 /api 代理 (Vite dev proxy, 解决跨域 + cookie 透传)
  │    /api/user/*   → http://user-svc.内网/...
  │    /api/order/*  → http://order-svc.内网/...
  │    /api/auth/*   → http://sso.内网/...        (自建 SSO)
  ▼
多个远端业务服务  +  自建 SSO 服务
```

### 为什么这样设计
- **cookie 鉴权要求同源**：浏览器对跨域 cookie 限制很严（SameSite / 第三方 cookie 拦截）。开发期统一走 `/api` 同源代理，由代理层透传 cookie，避免跨域 cookie 丢失。
- **多远端服务用「路径前缀」区分**：`/api/<service>/*` 各自映射不同 upstream，前端按服务建多个 Axios 实例，但共享拦截器逻辑。
- **header token + cookie 并存**：cookie 浏览器自动带（`withCredentials: true`）；header token 由拦截器统一注入。

## 三、目录结构（建议）

```
src/
├─ http/
│  ├─ createClient.js     # 工厂：创建带统一拦截器的 axios 实例
│  ├─ interceptors.js     # 请求/响应拦截器（cookie+header、401处理）
│  ├─ clients.js          # 各远端服务的实例（user/order/...）
│  └─ services.config.js  # 服务清单 → 前缀映射（单一数据源）
├─ auth/
│  ├─ sso.js              # 自建SSO：登录跳转、登出、校验登录态
│  └─ guard.js            # 页面登录门禁
└─ ...
.webgen/
└─ config.json            # 预览端口 + 多 upstream 代理规则
```

**`services.config.js` 作为单一数据源**，新增一个远端服务只改这里 + 代理配置，前端实例自动生成。
